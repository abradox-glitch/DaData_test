# Поиск основного сайта российской организации по ИНН

Небольшой агентный пайплайн для задания DaData. На вход принимает
российский ИНН, а на выходе всегда отдаёт JSON вида `{"domain": "example.ru"}`
или `{"domain": null}`.

## Структура проекта

Исходный код специально собран в один модуль, чтобы решение было легко
просмотреть на тестовом: [`site_finder/app.py`](site_finder/app.py).
Внутри него секции идут в порядке выполнения: контракты, утилиты, адаптеры API,
сбор evidence, LLM и orchestration. `site_finder/__main__.py` — только точка
входа, а `tests/test_app.py` содержит офлайн-проверки.

## Логика решения

```text
ИНН -> проверка контрольных цифр -> DaData (карточка организации)
    -> Web Search (до двух уточнённых запросов)
    -> фильтрация справочников/соцсетей + дедупликация доменов
    -> загрузка страниц-кандидатов
    -> LLM с JSON-контрактом
    -> проверка confidence и принадлежности домена кандидатам -> domain | null
```

1. Валидирую формат и контрольные цифры ИНН. Затем DaData даёт название,
   адрес, город, ОКВЭД, руководителя и (если доступно на тарифе) e-mail.
2. Выполняю два поисковых запроса: по точному названию и ИНН, затем по
   названию и городу. Из выдачи исключаю известные каталоги, карты, соцсети,
   маркетплейсы и вакансии. URL привожу к регистрируемому домену и дедуплицирую.
3. Для максимум шести кандидатов извлекаю title, description и ограниченный
   фрагмент видимого текста. Домен корпоративного e-mail — лишь дополнительный
   кандидат: сам по себе он не считается доказательством.
4. LLM получает карточку организации и этот фиксированный набор доказательств.
   Ей запрещено придумывать домены; она обязана вернуть строго JSON с доменом,
   confidence и кратким объяснением.
5. Код не доверяет ответу модели безусловно: домен нормализуется, обязан быть
   среди переданных кандидатов, а confidence должен быть не ниже `0.75`.
   Иначе возвращается `null`.

Такое разделение полезно для задачи с высокой ценой ложного совпадения:
поисковая система собирает кандидатов, LLM сопоставляет разнородные признаки,
а детерминированная часть ограничивает галлюцинации и неоправданно уверенные
ответы.

## Установка и запуск

Требуется Python 3.10+.

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -e .
Copy-Item .env.example .env
```

Заполните `.env`:

```dotenv
DADATA_API_KEY=...
SEARCH_PROVIDER=brave
BRAVE_API_KEY=...

# Любой OpenAI-совместимый LLM API. Например, для Groq:
LLM_API_KEY=...
LLM_BASE_URL=https://api.groq.com/openai/v1
LLM_MODEL=...
LLM_MIN_CONFIDENCE=0.75
```

Вместо Brave можно указать `SEARCH_PROVIDER=exa` и `EXA_API_KEY`. Провайдер LLM
не зашит в код: нужны только совместимые с Chat Completions URL, ключ и модель.

```powershell
python -m site_finder 7721581040
# {"domain": "dadata.ru"}
```

После `pip install -e .` доступна и короткая команда `site-finder 7721581040`.

Для проверки без сетевых вызовов:

```powershell
python -m unittest discover -s tests -v
```

## Технические решения и ограничения

- HTTP-клиенты имеют таймауты и retry для временных ошибок API; поисковый
  адаптер Brave также соблюдает минимальный интервал между запросами.
- HTML читается с лимитом размера; не-HTML, ошибочные URL и literal private IP
  игнорируются. Это уменьшает стоимость и риск обработки нерелевантных страниц.
- Если организация не найдена, нет кандидатов, доказательства противоречивы или
  модель отвечает вне контракта, безопасный результат — `null`.
- Решение зависит от индекса поисковой системы и от доступности текстовой версии
  сайта. У организаций с одинаковым названием или JS-only страницами уверенность
  будет ниже. Для промышленной версии я бы добавил кэш, журнал решений с
  evidence, список подтверждённых доменов и регулярную переоценку старых записей.

В проекте намеренно нет ключей и реальных ответов API.
